Upgrade Guides#

Ballista 56.0.0#

Note: Ballista 56.0.0 has not been released yet. The information provided in this section pertains to features and changes that have already been merged to the main branch and are awaiting release in this version.

Deprecations#

The scheduler’s embedded Flight proxy is deprecated#

--enable-embedded-flight-proxy (and SchedulerConfig::enable_embedded_flight_proxy) is deprecated and will be removed in 57.0.0. The proxy puts result traffic on the scheduler’s process, where it competes with query planning and task scheduling, and it scales only with the scheduler.

Deployments where clients cannot reach the executors should instead run the new ballista-result-service binary, a stateless Arrow Flight service that forwards each result fetch to the executor holding the partition, and point the scheduler’s --advertise-flight-endpoint at it, or at a load balancer in front of several replicas:

ballista-result-service --bind-port 50055
ballista-scheduler --advertise-flight-endpoint ballista-results.example.com:50055

For Kubernetes, see the example manifests in Serving Results to Clients Outside the Cluster.

Clients need no changes. The embedded proxy keeps working throughout 56.x, so you can compare the two and roll back without downgrading Ballista; the scheduler logs a warning at startup while it is enabled.

If you embed the scheduler and configure the proxy’s connections to executors with SchedulerConfig::use_tls and override_create_grpc_client_endpoint, for example for mTLS, run the result service from your own binary with ballista_result_service::serve. Its ResultServiceConfig takes the same two settings. The ballista-result-service binary connects to executors in plaintext, as the stock scheduler binary does.

Also deprecated:

  • SchedulerConfig::with_enable_embedded_flight_proxy

  • passing --advertise-flight-endpoint with no value, which starts the embedded proxy

Behavior changes#

Containers stop on SIGTERM#

The images’ entrypoints now exec their binaries, and each binary handles SIGTERM, so docker stop and pod termination reach the Ballista process. Before, the signal never did, and containers waited out their grace period to be killed. On Windows, Ctrl-Break and closing the console also start the shutdown, but Windows ends a console process about 5 seconds after its console closes, so a longer drain is cut short.

  • Executors now drain their running tasks before exiting, for up to --graceful-shutdown-timeout-seconds (10 by default). See Stopping executors for tasks that run longer.

  • The scheduler no longer exits at once on SIGTERM or Ctrl-C. It refuses new jobs with Unavailable, over gRPC and Flight SQL alike, lets its active jobs finish, and then drains its connections, all within --graceful-shutdown-timeout-seconds (25 by default). A second signal ends the shutdown at once, with an error. See Stopping the scheduler for how to size it and for how results fetched through the scheduler are served.

  • SchedulerConfig gains a graceful_shutdown_timeout_seconds field, so a struct literal that doesn’t end in ..Default::default() needs to set it. The public QueryStageSchedulerEvent::JobQueued gains an admission field.

  • scheduler_process::start_server_with_shutdown serves until the future that its shutdown argument returns completes, then shuts down as above; the binaries pass ballista_core::utils::shutdown_signal. start_server is unchanged and doesn’t handle signals.

  • The scheduler, the executor and the result service share one shutdown contract. After --graceful-shutdown-timeout-seconds they stop waiting and exit with an error, and 0 waits as long as the drain takes. The result service used to exit at once for 0, and to exit successfully on a timeout.

  • The CLI exits on SIGTERM.

  • ballista_executor::terminate::sig_term is deprecated. Use ballista_core::utils::terminate_signal, or shutdown_signal for Ctrl-C as well.

  • The standalone image stops its scheduler first, so that its active jobs can finish while the executor keeps running their tasks, and then its executor. The scheduler’s drain can outlast docker stop’s default of 10 seconds, so pass docker stop -t a time above --graceful-shutdown-timeout-seconds, 25 by default.

Undecodable fetch tickets are rejected as InvalidArgument#

Executors, the embedded proxy, and the result service now share one implementation of partition fetches. A DoGet ticket that does not decode as a Ballista action is reported with the gRPC status InvalidArgument everywhere; executors used to report it as Internal.

Pull-staged executors no longer run more partitions than they have vcores#

Under pull-staged scheduling (--scheduler-policy pull-staged on the scheduler, --task-scheduling-policy pull-staged on executors), which standalone mode also uses, an executor counted each task as one vcore however many partitions the task held. With ballista.scheduler.max_partitions_per_task at its default of 0, an idle 8-vcore executor could take an 8-partition task, still report 7 vcores free, and be handed another task on its next poll. It could end up running several times more partitions than it has vcores, with per-task memory pools that added up to more than its memory budget, while executors that polled later could get no work.

An executor now holds a task’s vcores until the task finishes, as with push-staged scheduling. That includes the vcores of partitions that finish early, so a straggler partition leaves them idle. Set ballista.scheduler.max_partitions_per_task to a positive value to dispatch smaller tasks, which release their vcores sooner.

API changes#

sort_shuffle::BufferedBatches is no longer public#

ballista_core::execution_plans::sort_shuffle::BufferedBatches, the sort-shuffle writer’s internal row buffer, is no longer exported. It had no use outside the writer. Code that used it directly should use SortShuffleWriterExec instead.

TaskManager::executor_lost also returns jobs that lost cached data#

ballista_scheduler::state::task_manager::TaskManager::executor_lost now returns (Vec<RunningTaskInfo>, Vec<(JobId, u64)>) instead of Vec<RunningTaskInfo>. The second element lists the jobs that lost DataFrame::cache() data with the executor, with when each was queued. Their graphs are not reset, because they cannot re-run another job’s output, so a caller must fail them (the scheduler posts JobRunningFailed). A caller that only needs the tasks to cancel can take the first element.

Python client changes#

Summary#

  • The Ballista Python client now plugs into DataFusion Python natively. It registers a custom query planner on a standard datafusion.SessionContext, instead of wrapping DataFusion classes.

  • DistributedDataFrame and the metaclasses that wrapped SessionContext and DataFrame are removed. Queries return a plain datafusion.DataFrame.

  • BallistaSessionContext is now a factory function that returns a datafusion.SessionContext, not a class.

  • explain_visual and collect_with_progress are no longer DataFrame methods. They are functions in ballista.jupyter.

  • Ballista settings are registered as a DataFusion config extension, exposed as BallistaConfigExtension.

DataFusion Python is supported natively#

Earlier releases subclassed SessionContext and DataFrame. Every method that executed a plan was intercepted, the logical plan was serialized, and the plan was resubmitted through a separate, Ballista-backed session. Methods the wrapper did not know about ran locally, and every execution created a new Ballista session.

In 56.0.0, BallistaSessionContext installs a Ballista query planner and extension codecs on a standard DataFusion Python SessionContext, using DataFusion’s FFI. DataFusion plans each query as usual, and the planner sends the physical plan to the scheduler. Any operation that executes a plan runs on the cluster, including collect, show, to_pandas, write_parquet and EXPLAIN ANALYZE. No wrapper is involved.

DistributedDataFrame is removed#

ballista.DistributedDataFrame no longer exists, and ballista.extension no longer exports it. ctx.sql(...), ctx.read_parquet(...) and the other context methods return a regular datafusion.DataFrame.

Action required: remove imports of DistributedDataFrame, and replace type hints and isinstance checks with datafusion.DataFrame:

# before
from ballista import DistributedDataFrame

def run(df: DistributedDataFrame): ...

# after
from datafusion import DataFrame

def run(df: DataFrame): ...

BallistaSessionContext is a factory function#

BallistaSessionContext keeps its name and call signature, so existing code that creates a context does not change:

from ballista import BallistaSessionContext

ctx = BallistaSessionContext("df://localhost:50050")

It is now a function that returns a datafusion.SessionContext. It is not a class. Code that depends on it being a class breaks:

  • isinstance(ctx, BallistaSessionContext) raises TypeError. Use isinstance(ctx, datafusion.SessionContext).

  • Subclassing BallistaSessionContext is no longer possible. Create a context and pass it to your own code, or wrap it.

  • ctx.session_id is no longer a property. Call ctx.session_id(), as on any DataFusion SessionContext.

  • The ctx.address and ctx.cluster_config attributes are removed.

  • ctx.get_tables() is removed. Use the DataFusion catalog API, for example ctx.catalog().schema("public").table_names().

Configuration changes#

cluster_config values can now be str, int, float or bool. Booleans are converted to "true" and "false". Keys must start with datafusion. or ballista.. Any other key raises ValueError:

ctx = BallistaSessionContext(
    "df://localhost:50050",
    cluster_config={
        "datafusion.execution.target_partitions": 16,
        "ballista.job.name": "daily report",
        "ballista.planner.adaptive.enabled": True,
    },
)

Ballista settings are registered on the session as a DataFusion config extension, available as ballista.BallistaConfigExtension. As a result, ballista.* keys appear in information_schema.df_settings and can be changed with SQL SET, for example SET ballista.job.name = 'nightly'.

The local session now starts from Ballista’s DataFusion defaults, the same defaults the scheduler uses. Some DataFusion options are restricted by Ballista (for example datafusion.optimizer.prefer_hash_join and datafusion.optimizer.enable_round_robin_repartition). These options are always set to the Ballista value, even if you set them in config. Other Ballista defaults, such as datafusion.optimizer.hash_join_single_partition_threshold, can still be overridden when config is passed as a dictionary.

Jupyter support changes#

DataFrame.explain_visual() and DataFrame.collect_with_progress() were methods of DistributedDataFrame and are removed with it. They are now functions in ballista.jupyter that take the DataFrame as their first argument:

from ballista.jupyter import collect_with_progress, explain_visual

df = ctx.sql("SELECT * FROM orders WHERE amount > 100")

# before: df.explain_visual()
explain_visual(df)
explain_visual(df, analyze=True).save("plan.svg")

# before: df.collect_with_progress()
batches = collect_with_progress(df)
batches = collect_with_progress(df, callback=lambda status, progress: print(status))

The parameters and return values are unchanged.

The %sql magic returns a datafusion.DataFrame instead of a DistributedDataFrame. %ballista tables uses the DataFusion catalog directly, since ctx.get_tables() is removed. %ballista status shows the session id from ctx.session_id(). The magic commands themselves are unchanged.
