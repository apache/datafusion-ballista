Comparison with DataFusion Distributed#

DataFusion Distributed is another project that runs Apache DataFusion plans across many machines. Both projects are open source, both are built on the same query engine, and both stream Arrow data over gRPC. Users reasonably ask how they differ, which one to choose, and whether one could be built on top of the other. This page answers those questions. It is likely biased, because the Ballista community maintains it.

In short: Ballista is a distributed query engine, and DataFusion Distributed is a library for building one. Ballista ships a scheduler, executors, clients, and the machinery for running many jobs on a shared cluster and surviving the loss of an executor. DataFusion Distributed adds a small set of operators and a planner to DataFusion so that an existing system can spread one query over workers it already manages, and leaves deployment, worker discovery, and cluster management to that system.

Execution models#

Ballista started with the execution model of Apache Spark. Each query stage runs to completion and writes its output to local storage before the next stage starts (a blocking shuffle). That output outlives the task that wrote it, which is what lets Ballista recover from a lost executor by re-running only the lost tasks, run a query wider than the cluster, and plan the rest of a query from exact statistics. Shuffle Design explains this model and its costs in detail.

Ballista is adding a second, pipelined execution model, in the style of Trino, as an experimental option chosen per job with ballista.execution.mode = pipelined. All of a job’s tasks are placed up front and stages stream batches to each other through bounded in-memory queues, with nothing written to disk. The configuration and the pipelined exchange operators are on main (#2670, #2685); the scheduler support that runs pipelined jobs end to end is in review in #2657.

DataFusion Distributed has one execution model, the pipelined one. Its documentation is clear about the trade-off:

If any node fails mid-query, the whole query fails; there are no retries. There’s no persistence of intermediate results, so queries can’t checkpoint or resume from where they stopped.

So the choice between them is no longer “batch versus interactive”. Once pipelined mode is complete, a Ballista cluster will run long ETL jobs with the blocking model and low-latency analytical queries with the pipelined model, side by side on the same scheduler and executors. DataFusion Distributed is designed for the second kind of workload.

Why Ballista can’t build on DataFusion Distributed#

The two projects overlap in one place: how a plan is split into stages and how data moves between them. Everything else Ballista provides sits above that layer, and DataFusion Distributed deliberately leaves it out. Its stated goal is to remain “a library, not an engine” that is “unopinionated about networking”. Rebuilding Ballista on it would therefore replace only the part that Ballista needs to own in order to offer both execution models.

Ballista’s blocking model needs a scheduler that sees stages. Recovery in Ballista works because the scheduler knows when each stage has completed, where its output lives, and which tasks to re-run when an executor disappears. DataFusion Distributed’s coordinator is scoped to a single query and is built around all stages running at once. In its default mode it sets up every stage’s tasks before the query’s final stage runs, keeps only the worker addresses of a stage once its plan has been sent, and treats a worker failure after routing as a query failure. Its transport is pluggable through the WorkerChannel trait, and a disk-backed implementation has been suggested as a way to bring Ballista’s model to it. A channel can make a producer’s output re-readable, but it cannot decide that a stage has finished, keep the plan needed to re-run part of it, or move a task to another worker. Those are coordinator responsibilities. Adding them would turn DataFusion Distributed into an engine, against its own design, or leave Ballista running its own scheduler on top of a second coordinator.

Exact statistics come from completed stages. Ballista’s adaptive planner re-optimizes the remaining plan after each stage finishes, using measured row and byte counts. That includes decisions that need a final answer, such as removing work below an input that turned out to be empty. DataFusion Distributed’s adaptive execution samples batches from running stages to size later ones. Both approaches are sound, but they need different contracts between the planner and the exchange. See Shuffle Design for more on this distinction.

The building blocks Ballista would keep are most of Ballista. These include the executor lifecycle, vcore accounting and placement across many jobs, per-task memory pools, multi-partition tasks, the DataFrame cache, the clients, the REST API, event logs, and the history server. They would all remain, on top of a dependency whose coordination model differs from theirs.

Ballista’s own APIs would gain a second source of churn. Users extend Ballista through its codecs, planners, and producers, and follow DataFusion’s release cadence. DataFusion Distributed is moving quickly, with four major releases so far, and marks WorkerChannel as unstable. That is reasonable for a young library, but building Ballista on it would pass those changes on to Ballista’s users.

The reverse does not work either. DataFusion Distributed’s users choose it because it embeds into an existing system as an extension of DataFusion, with no scheduler or executor processes to run. Ballista cannot offer that.

Where the projects can share work#

The overlap is real and likely to grow, as Ballista’s pipelined mode moves into the space DataFusion Distributed targets. The most useful place to share work is DataFusion itself. Several DataFusion and Arrow improvements have already come from DataFusion Distributed, such as range partitioning that avoids unnecessary shuffles (datafusion#23184, datafusion#24598), dynamic filters that can be sent over the network (datafusion#21807, datafusion#24068), and IPC and Flight optimizations (arrow-rs#10044, arrow-rs#10273). Both projects benefit from those. Other shared pieces, such as an exchange abstraction or a common way to split a plan into stages, would also be best placed in DataFusion, where any distributed engine can use them.

Performance#

The results below compare the two projects on the same hardware and data, with each given the same resources. Both use the same query engine, both are open source, and both are improving quickly. Treat the gaps as a snapshot of two moving targets rather than a fixed property of either design, and expect them to narrow as each project adopts what works in the other.

Setup. TPC-H at scale factor 1000, Parquet files compressed with zstd, read from Amazon S3. The tables are Hive-partitioned (lineitem and orders by date), and both projects declared the partition columns so that they prune partitions. Kubernetes on AWS, with 32 workers (Ballista executors) of 8 vCPU and 64 GiB each. Each query ran twice with no warm-up, so the first, cold run is included in the mean.

  • Ballista was built from #2657 at commit cb49f30f (DataFusion 55.2.0). Each executor ran 8 tasks with a memory pool of 70% of its memory, and target_partitions was 256. The same image ran the blocking and pipelined modes.

  • DataFusion Distributed was built from main at commit 90350275 (DataFusion 55.0.0), using the worker from its benchmarks/remote-worker crate. Upstream’s worker has an unbounded memory pool, so it was patched to give each worker a fair spill pool of 70% of its memory, like Ballista’s executors. A separate 8 vCPU, 32 GiB pod ran the coordinator and the final stage of each query. Its settings were otherwise the defaults.

What the results show.

  • Pipelined Ballista and DataFusion Distributed are close, which is expected of two pipelined engines on the same query engine. Ballista was faster on 17 of the 22 queries and DataFusion Distributed on 5 (Q1, Q4, Q7, Q18, and Q21). The geometric mean of the per-query ratios favours pipelined Ballista by about 1.4x.

  • Most of the difference in the total is Q16. DataFusion Distributed runs the final COUNT(DISTINCT) aggregation and anti join of Q16 on the coordinator, over 8 partitions. With the coordinator’s 22.4 GiB memory pool, that stage spilled 7.2 GB, and it was the only stage in the run that spilled. Excluding Q16, the geometric mean favours pipelined Ballista by about 1.2x.

  • Blocking Ballista was about 1.85x slower than pipelined Ballista in total, which is the latency cost of writing every stage’s output to disk before the next stage starts.

Caveats.

  • Each query ran only twice, so per-query differences of less than about 10% are within run-to-run variation.

  • The setups are as close as we could make them, but not identical. DataFusion Distributed’s coordinator is an extra pod that runs part of each query, while Ballista’s scheduler runs no query work. The two projects were also on different patch releases of DataFusion.

  • DataFusion Distributed’s README publishes a comparison in which Ballista is slower than it by a wide margin, on a 12-node cluster at scale factors up to 100. That comparison was last updated in July 2026 and used Ballista 53.0.0. Ballista has had two releases and more than 500 commits since. Those include adaptive query execution enabled by default (#2315) and tasks that cover several partitions (#2038). The pipelined mode was not available then.

  • Corrections to either setup are welcome. Please open an issue.
